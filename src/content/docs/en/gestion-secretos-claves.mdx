# Secrets and keys: rotation without surprises

A database password pasted into a configuration file looks like a small detail until the repository goes public or a log
line prints it into a trace. The risk lies not only in the code but in who can read the secret and for how long it stays
valid.

## Why secrets do not belong in the repository

Git keeps history. Deleting a file in a new commit does not remove the secret from earlier commits, and anyone with read
access can recover it. So the rule is not to remove it from the latest commit; it is to treat the secret as compromised the
moment it touched the repository, and rotate it.

## Vaults and managers

A vault stores secrets encrypted, controls who may request them, records every read and allows revocation. Its value is not
encryption, which almost every platform offers, but three properties: a single point of lookup, an audit trail of access, and
the ability to change a secret without deploying code. What matters is having one source of truth.

## Workload identity versus static secrets

The best secret is the one that does not exist. A workload running in the cloud can present an identity signed by the
platform, such as an assigned role, and receive a short-lived credential from the vault. No permanent key remains to steal.
When no identity is available, a static secret becomes unavoidable: limit its scope, its permissions and its rotation interval.

## Rotation with two active keys

Rotating a secret used by one application is easy. The problem appears when dozens of services read it. The usual technique
keeps two keys active: the new one is published, each consumer adopts it at its next read, and once the old key's usage
reaches zero, it is revoked.

Take a payment service with an API key rotated every 90 days, read by 40 consumers that refresh the secret every 15 minutes.
Full adoption takes about 15 minutes. With a 24-hour overlap window there is ample margin for services that restart late. If
the old key were revoked after five minutes, any consumer that had not yet re-read the secret would fail.

## Encryption keys: hierarchy and envelopes

Encrypting everything with one key for years is a risk. Envelope encryption encrypts each piece of data with its own data key,
and that data key with a master key kept in the key manager. Rotating the master key only requires re-wrapping the data keys,
not re-encrypting all storage. Rotating a data key does require re-encrypting the data, so rotate the master key more often and the
data keys less often, since each data-key rotation requires re-encrypting data.

## Auditing and leaks

Three controls help detect leaks: a secret scanner at pre-commit and in the pipeline, alerts on unusual vault reads, and a
written procedure for rotating when a leak is suspected. Rotate first and investigate afterwards, because every minute of
delay is a minute of exposure.

## Common mistakes

- Storing the encrypted secret in the same repository as the key that decrypts it.
- Believing that deleting the file is enough.
- Reusing the same secret in tests and in production.
- Rotating without measuring who still uses the old key.

## When it does not apply

A local prototype with test data does not need a vault. As soon as someone else runs it, the secret must leave the code.
Building a full manager for a one-person application makes no sense.

## Checklist

- [ ] Is there any secret in the git history? If so, rotate it.
- [ ] Do cloud workloads use identity instead of static keys?
- [ ] Does each rotation have a two-key window and a usage metric for the old key?
- [ ] Does the data use envelope encryption with separate keys?
- [ ] Are there alerts for unusual reads and a written leak procedure?
