# Edge and CDN: what to run at the edge

A content delivery network (CDN) keeps copies of resources on nodes close to users, and those nodes can now also run small
functions before answering. The architectural question is no longer whether to use the edge, but what should run there and what
must stay at the origin.

## What a CDN serves well

A CDN works well for responses that are identical for many users for a while: images, scripts, stylesheets, public pages or
read-only responses. Anything that depends on each user, such as an account balance, must go to the origin or be personalised
explicitly. A practical rule: cache what is the same for many and changes rarely, and leave at the origin what is unique per user
or changes on every write.

## Latency against cost

Moving the answer closer cuts network latency, but not computation or data access. With a user 20 ms from the edge and 200 ms from
the origin, a 90 % hit rate gives an average latency of 0.9 × 20 + 0.1 × (20 + 200) = 40 ms. At 60 % it rises to 0.6 × 20 + 0.4 ×
220 = 100 ms. The hit rate, not proximity alone, decides the experience.

Cost changes too: each node that runs code is billed per invocation and per time, and traffic leaving the edge has its own rate. A
calculation that looks only at latency can reject an option that turns out more expensive than it seems.

## What can run at the edge

Edge functions suit small decisions that need no full data: rewriting a URL, choosing a page variant by language, validating a header
or checking a signed token. They are a poor fit for logic that needs a lot of data or shared state, such as a price calculation that
reads inventory. Providers limit time, memory and data access; if a function needs three queries to a central database, it probably
belongs at the origin.

## Invalidation and TTL

The TTL sets how out of date a copy may be. A long TTL reduces origin load but is slow to reflect a change; a short one lowers the risk
but increases origin requests. A common strategy combines moderate TTLs with explicit invalidation when content is published, and serves
the stale copy while refreshing it in the background when a few seconds of delay are acceptable. Invalidation takes time to reach every
node, so versions coexist for a while.

## Consistency across nodes

Each node has its own cache, so two users in different regions can see different versions for a while. For resources that vary per user,
the cache key must include the headers or cookies that change the response; otherwise one user may receive another's page. Consistent
hashing spreads keys across nodes so that every node does not store the same things.

## Data that must stay at the origin

Writes, transactions and sensitive personal data should stay at the origin or in a controlled region. Moving them to the edge multiplies
copies and complicates compliance with data-protection rules.

## When the edge does not pay off

It does not pay off when requests rarely repeat, when users are already close to the origin, when the logic needs central data, or when the
team cannot observe code spread over many points. A well-configured cache at the origin is then usually cheaper and easier to run.

## Common mistakes

- Caching personalised responses without including the headers that make them different.
- Moving to the edge logic that queries a central database on every request.
- Measuring only average latency, not the hit rate or the 95th percentile.
- Assuming invalidation is immediate in every region.

## Checklist

- [ ] Which responses are identical for many users, and for how long?
- [ ] Does the cache key include everything that changes the response?
- [ ] Is there an invalidation plan, and is mixed versions during propagation acceptable?
- [ ] Is the edge logic small and free of central data needs?
- [ ] Do personal data and writes stay in a controlled region?
